# 版本、兼容与迁移所有权

- 状态：Accepted
- 日期：2026-08-27
- 范围：REST、WebSocket、Runtime 协议、事件、配置、持久化结构与 Release

## 问题

项目处于 `v0.x`，内部契约仍会快速演进，但已经存在发布制品、用户配置、设备协议和持久化数据。把“未到 1.0”理解为所有内容都可无条件破坏，会损坏真实用户状态；反过来，为每次变化臆造别名、双读双写和 fallback，又会形成多个权威并长期拖慢实现。

## 决定

兼容不是默认动作，也不是默认禁止项，而是由已核验的消费者和数据决定：

- 仅在仓库内部使用、且全部当前生产者和消费者能在同一变更中更新的契约，直接替换权威定义并清理旧路径。
- 已发布配置、跨版本设备协议、公开 API 或持久化数据发生变化时，先核验当前消费者、升级路径和数据价值，再决定迁移或破坏性替换。
- 不得为了“稳妥”增加没有当前消费者证据的旧字段、别名、双写、双读、旧 RPC、兼容开关或静默 fallback。
- 确需保留兼容时，决定必须记录兼容所有者、适用版本、退出条件和删除目标；兼容层不能成为第二权威来源。
- 每个存储拥有自己的迁移策略。`control.db` 使用显式事务迁移；特定工作区聊天数据库的精确重建策略只在对应 ADR 的数据域和完整性前提下成立，不推广到 Session、配置或其他用户数据。
- 能力探测只报告当前能力，不能用作切换到未声明旧协议的入口。
- 已发布 tag 不移动。修复通过新提交和后续版本交付，Release manifest、协议/schema 元数据和用户文档随权威契约一起更新。

## 后果

- 实现前需要找到真实消费者和存量数据，而不是从版本号推导兼容策略。
- 直接替换时必须同步删除需求范围内的旧生产者、消费者、测试和文档。
- 迁移或兼容的成本、期限与退出动作成为显式架构决定，不能隐藏在运行时 fallback 中。
- 若新的业务架构取代既有 ADR，必须用新的 Accepted ADR 明确 supersede；未提交的工作树不构成稳定决定。
